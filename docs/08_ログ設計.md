# ログ設計

← [要件定義書に戻る](../要件定義書.md)

---

## 目的

バックエンド（Spring Boot）のログを **JSON形式の構造化ログ** として出力する。
現時点ではDataDog等の監視SaaSは導入しないが、コンテナのstdoutにJSONログを出しておくことで、
将来DataDog Agent（Log Collection）を追加するだけで取り込みが可能な状態にする。

対象はバックエンドのみ。フロントエンド（React）のログ整備は対象外。

---

## ログ基盤の構成

| 項目 | 内容 |
|------|------|
| ロギングAPI | SLF4J（Spring Boot標準） |
| 実装 | Logback |
| 出力形式 | JSON（`net.logstash.logback:logstash-logback-encoder`） |
| 出力先 | 標準出力（stdout） |
| 設定ファイル | `backend/src/main/resources/logback-spring.xml` |

Docker運用を前提に、ログファイルへの出力は行わない。コンテナのstdoutをログドライバー（Docker logging driver）経由でDataDog Agent等が収集する想定。

---

## ログフィールド

すべてのログに以下の基本フィールドが付与される。

| フィールド | 内容 |
|-----------|------|
| `timestamp` | ログ出力時刻 |
| `level` | ログレベル（INFO/WARN/ERROR） |
| `logger` | 出力元クラス（ロガー名） |
| `message` | ログメッセージ |
| `thread` | スレッド名 |
| `service` | サービス名（`raisetimeline`固定） |
| `stack_trace` | 例外発生時のスタックトレース |

リクエスト処理中は以下のMDC（Mapped Diagnostic Context）フィールドが付与される（`config/RequestLoggingFilter.java`で設定）。

| フィールド | 内容 |
|-----------|------|
| `requestId` | リクエストごとに発行するUUID。1リクエストの全ログを紐付けるためのキー |
| `method` | HTTPメソッド |
| `path` | リクエストパス |
| `userId` | 認証済みユーザーのID（JWT認証成功時のみ） |

業務ログのメッセージは `event=<ドメイン>.<操作>.<結果>` の形式に統一し、続けて関連IDをキー・バリューで付与する。

例: `event=post.create.success userId=12 postId=345`

DataDog導入後は `event` フィールドをログベースメトリクスの集計キーとして利用できる。

---

## ログレベル方針

| レベル | 用途 |
|--------|------|
| `INFO` | 正常な業務操作（投稿作成、いいね、ログイン成功など）、アクセスログ |
| `WARN` | クライアント起因のエラー（4xx系: バリデーションエラー、404、403、ログイン失敗など） |
| `ERROR` | サーバー起因の想定外エラー（5xx系: S3アクセス失敗、DB例外、ハンドリングされない例外） |

local環境ではアプリケーションパッケージ（`com.example.raisetimeline`）のログレベルを`DEBUG`、それ以外の環境では`INFO`とする。

---

## アクセスログ

`config/RequestLoggingFilter.java` が全リクエストに対して以下を出力する。

- リクエストごとに`requestId`を発行しMDCに設定
- レスポンス確定後、`event=http.access status=<HTTPステータス> durationMs=<処理時間>` をINFOで出力

このフィルターは`SecurityConfig`で`JwtAuthenticationFilter`より前段に登録されており、認証後にセットされた`userId`もログに含まれる。

## 業務イベントログ一覧

| 機能 | クラス | イベント | レベル |
|------|--------|---------|--------|
| 認証 | `AuthService` | `auth.register.success` | INFO |
| 認証 | `AuthService` | `auth.login.success` | INFO |
| 認証 | `AuthService` | `auth.login.failure`（メール不存在／パスワード不一致） | WARN |
| 認証 | `AuthService` | `auth.refresh.failure`（期限切れ） | WARN |
| 認証 | `JwtTokenProvider` | `auth.jwt.validation_failure` | WARN |
| 投稿 | `PostService` | `post.create.success` / `post.delete.success` | INFO |
| コメント | `CommentService` | `comment.create.success` / `comment.delete.success` | INFO |
| いいね | `LikeService` | `like.add.success` / `like.remove.success` | INFO |
| フォロー | `FollowService` | `follow.add.success` / `follow.remove.success` | INFO |
| 画像アップロード | `S3Service` | `s3.upload.success` | INFO |
| 画像アップロード | `S3Service` | `s3.upload.failure`（S3例外） | ERROR |
| 例外処理全般 | `GlobalExceptionHandler` | `exception.not_found` / `exception.forbidden` / `exception.conflict` / `exception.bad_request` / `exception.validation` | WARN |
| 例外処理全般 | `GlobalExceptionHandler` | `exception.unexpected`（想定外例外） | ERROR |

## 将来のDataDog連携イメージ

1. DataDog Agentをホスト/コンテナに導入し、Dockerログドライバー経由でstdoutのJSONログを収集する
2. JSON形式のため、Agent側での追加パース設定なしにフィールド（`event`, `userId`, `level`等）を構造化フィールドとして認識できる
3. `event`フィールドをキーにLog-based Metricsを作成し、`09_監視アラート設計.md`の指標・アラートに利用する

設定ファイル（datadog.yaml等）やAPIキーの導入は本ドキュメントの対象外とし、実際にDataDogを導入する際に別途対応する。
